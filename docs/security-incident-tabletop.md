# Security incident tabletop — paper exercise

Status: template. This exercise has not been run yet; no dates, participants or results are recorded here.

This is a paper exercise. Do not access production, inspect credentials, notify users, revoke access, roll back a deployment, or change services while running it. A facilitator reads each case; participants record a decision owner, evidence, next proposed action and stop condition. Use role names until actual people have been assigned through the [adoption checklist](security-incident-response.md#adoption-checklist).

| Scenario | Decision owner | Evidence to request | Proposed next action | Stop condition |
| --- | --- | --- | --- | --- |
| An npm advisory appears before a release. The package may be in the lockfile; reachability is unknown. | Incident lead requests a hold; release operator enforces it. Security reviewer judges reachability and severity. | Advisory URL and time, exact package/version and lockfile path, candidate commit, `verify / release-check` audit/signature result, dependency use in the built asset. | Hold publication. Review exposure and fix or documented exception under the [release gate](release-security.md); rerun it on the exact candidate. | No release until the affected version and decision are recorded and all required checks pass. A registry outage is unknown, not clean. |
| A malicious dependency is confirmed in a published asset. | Incident lead sets severity; authorized release operator decides maintenance/rollback path; communications owner drafts guidance. | Hosted asset hash and time window, workflow artifact and commit, dependency provenance, known safe artifact, observed behavior, headers, possible Google token or statement-password exposure. | Stop use of the affected page where authorized, preserve evidence, choose a verified clean artifact or maintenance, draft a factual user notice. If exposure warrants it, advise Google authorization review and provider password change. | Do not reopen or state “safe” until clean inputs, exact published artifact and headers are checked; do not rebuild from the suspect environment. |
| A Cloudflare deployment appears without an authorized release. | Incident lead treats as deployment-identity compromise until disproved; authorized hosting owner handles account actions. | Cloudflare deploy time, identity, route and asset, source commit/build ID, GitHub workflow history, enabled Builds/direct Wrangler paths, last verified safe artifact. | Pause publication paths with owner approval, preserve provider metadata, investigate account access, prepare credential rotation and verified rollback or maintenance. Communications owner drafts an uncertainty-aware update if users may be affected. | No credential or production action without authorized operator; no reopening until deployment paths and current hosted artifact are verified. |

For each scenario, write down: who can actually halt publication; how a known safe artifact is found; which proposed actions require external authorization; the truthful message possible with current evidence; and the next update time. Mark missing access or unknown provider configuration as an adoption prerequisite. The exercise passes only when each case has an accountable human decision path and an explicit stop condition; it does not prove a real incident can be detected or contained.
